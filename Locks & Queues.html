Module 1 · 20 min

Process synchronization

It all starts with one fact: counter = counter + 1 is not atomic. It is three steps: read, compute, write. When two workers interleave those steps, one write overwrites the other. That is a race condition, and the piece of code that only one worker may run at a time is a critical section.

Node.js runs JavaScript on a single thread, yet races still happen: between two awaits, other requests get to read the same data. The classic case: two HTTP requests check stock at the same moment, both see "1", both sell.

Tools worth knowing by name

Mutex

A lock with a single owner. Whoever takes it releases it. Guards a critical section.

Semaphore(N)

A counter of permits. Lets at most N in at once: a DB connection pool, a limit of 5 parallel API calls.

Read-write lock

Many readers together, or one writer alone. Useful when reads vastly outnumber writes.

Atomic / CAS

Compare-and-swap: "write X only if the current value is Y". The basis of lock-free structures and optimistic locking.

Pessimistic lock

Lock first, then work. SELECT … FOR UPDATE. Good when conflicts are frequent.

Optimistic lock

Work without a lock, check the version on write: UPDATE … WHERE version = 7. Zero rows updated means retry. Good when conflicts are rare.

DeadlockA holds lock X and waits for Y; B holds Y and waits for X. It needs all four Coffman conditions: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one and deadlock is impossible. In practice: always take locks in the same order (for example, by ascending id) and set a timeout.

Atomic operation or lock?

The deciding question: does "check and change" fit into one statement against one store? If yes, an atomic operation is enough. If something else sits between the check and the write, you need a lock.

Race: the check lives in code, the write in the DB
const { qty } = await db.one('SELECT qty FROM stock WHERE id = 5');
if (qty > 0) {                      // another request also sees qty = 1 here
  await db.none('UPDATE stock SET qty = $1 WHERE id = 5', [qty - 1]);
}
Atomic: check and change in one statement
const res = await db.result('UPDATE stock SET qty = qty - 1 WHERE id = 5 AND qty > 0');
if (res.rowCount === 0) throw new Error('Out of stock');

There is still a lock in the atomic version: the database locks the row for the few milliseconds the UPDATE runs. You just don't manage it yourself. Three questions to decide:

  • Is everything I check and change in one store? Postgres plus an external API means database atomicity can't cover it.
  • Can the condition go into WHERE? qty > 0, used < 100, version = 7, status = 'pending'. Then it's an atomic statement.
  • Is there anything external between the check and the write? An HTTP call, file generation, sending an email, long computation. No WHERE covers that; you need a lock.
TaskTool
Decrement stockUPDATE … SET qty = qty - 1 WHERE qty > 0

Rule of thumbGo up the ladder only as far as you need: conditional UPDATE or constraint → transaction with FOR UPDATE or optimistic version → distributed lock. Keep slow external calls out of DB transactions, or the row stays locked for the whole call.
Module 2 · 25 min

Distributed locks

A mutex lives in one process's memory. Once you have 3 API instances behind a load balancer or 5 workers on different machines, they need to agree through something shared: Redis, a database, etcd, ZooKeeper.

Typical jobs: only one instance runs a cron task; only one worker processes order #123; don't send a user the same email twice.

Two different purposes

Efficiency lock

Prevents duplicate work. If two workers occasionally do the job together, nothing breaks (an extra email, a recomputed cache). Single-node Redis is fine.

Correctness lock

Protects data from corruption (money, stock). Here the lock alone guarantees nothing: you need a fencing token or a transaction in the storage itself.

Redis: the correct minimum

redis-cli
# acquire: only if the key doesn't exist (NX), TTL 10 s (PX), value = unique token
SET lock:order:123 "c1-8f3a…" NX PX 10000

# release: only if the lock is still mine (atomically, via Lua)
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else return 0 end
  • TTL is mandatory, otherwise a crashed process holds the lock forever.
  • A unique value, because without it a client whose lock already expired will delete someone else's lock.
  • A Lua script, because GET and DEL as separate commands create a race again.
The problem people rarely mentionThe TTL runs out while the client is "asleep": a GC pause, swapping, a stalled network. The client wakes up sure it still holds the lock and writes to the database, while someone else already holds it. No algorithm on the lock server's side (including Redlock across 5 Redis nodes) fixes this.
Lab 2GC pause and the fencing token

Step through the scenario. Then switch to fencing token and go again. The difference is in the last step.

    Step 0 of 6

    A fencing token is a monotonically increasing number the lock service hands out with every lock. The storage remembers the highest token it has seen and rejects writes with an older one. In SQL it's a single condition:

    SQL
    UPDATE orders SET status = 'paid', fence = $token
WHERE id = $id AND fence < $token;   -- 0 rows = my lock is stale

    What to build it on

    ToolHowWhen to choose
    Redis (1 node)SET NX PX + Lua releaseEfficiency lock, Redis already in the stack, speed matters
    Redlock (5 nodes)Lock on a majority of independent Redis nodesDebated. Kleppmann's critique: depends on clocks and gives no fencing token
    PostgreSQLpg_advisory_lock(42), SELECT … FOR UPDATE SKIP LOCKEDData already in Postgres. The simplest route to correctness
    etcd / ZooKeeperLease + revision / ephemeral sequential znodeCorrectness, leader election. Revision or zxid acts as a fencing token
    In shortTo deduplicate cron jobs, Redis SET NX PX with a unique token is enough. If the lock protects money, add a fencing token checked by the database, or skip the distributed lock entirely: a conditional UPDATE, a unique constraint, or partitioning tasks by key so each key is handled by one worker.
    Module 3 · 15 min

    Message queues: why and with what guarantees

    A queue sits between whoever creates work and whoever does it. The producer drops a message and moves on; the consumer picks it up at its own pace.

    Decoupling

    The order service knows nothing about email, analytics, or the warehouse. It just publishes order.created.

    Load leveling

    A 5,000 RPS spike lands in the queue; workers drain it at 500/s. Nothing falls over.

    Async

    The user gets 202 Accepted in 30 ms; the PDF gets generated later.

    Retries and fault isolation

    Email service down for an hour? Messages wait in the queue instead of getting lost.

    Delivery semantics

    GuaranteeHow you get itRisk
    At-most-onceAuto-ack: the broker deletes the message as soon as it's deliveredConsumer crashes, message is lost
    At-least-onceManual ack after processingDuplicates: crashed after the work but before the ack
    Exactly-onceAt-least-once + idempotent consumerNot achievable over a network as such. You build the "exactly once" effect yourself
    Idempotent consumerEvery message carries a messageId. In the same transaction as the business write, the consumer inserts that id into a processed_messages table with a unique constraint. A duplicate hits the constraint and is simply acked. Module 5 walks through it step by step.
    Dual write and the Outbox pattern"Write to the DB and publish to the queue" spans two systems with no shared transaction. Crash in between and they drift apart. The fix: in the same transaction, write the event into an outbox table, and let a separate process (or CDC such as Debezium) move it to the broker.
    Module 4 · 25 min

    Inside RabbitMQ

    The key thing to remember: a RabbitMQ producer never writes to a queue directly. It writes to an exchange with a routing key. The exchange uses bindings to decide which queues get a copy. Consumers read from queues.

    Producer→ routing key →Exchange→ bindings →Queue(s)→Consumer(s)→ ack
    direct

    Exact match between routing key and binding key. Route tasks by type.

    topic

    Dot-separated patterns: * = exactly one word, # = zero or more words.

    fanout

    Ignores the key, a copy goes to every bound queue. Pub/sub, broadcast.

    headers

    Routes on headers instead of the key. Rarely used.

    What makes delivery reliable

    Manual ack

    The consumer confirms after processing. If the connection drops before the ack, the message goes back to the queue with redelivered = true.

    Prefetch (QoS)

    ch.prefetch(10): at most 10 unacked messages per consumer. Without it, a fast and a slow worker get equal shares and the slow one drowns.

    Durable + persistent

    A durable: true queue survives a broker restart; a persistent: true message is written to disk. You need both.

    Publisher confirms

    The broker confirms to the producer that it accepted the message. Without this, publish is "send and hope".

    Dead letter exchange

    Rejected (nack without requeue), TTL-expired, or over-the-delivery-limit messages go to the DLX and from there into a dead-letter queue for inspection.

    Quorum queues

    A replicated queue built on Raft. The modern default for clusters, replacing the old mirrored queues.

(async () => {

  await ch.assertExchange('orders', 'topic', { durable: true });

    worker.js
    const amqp = require('amqplib');
const [, , queue = 'q.email', pattern = 'order.#'] = process.argv;

(async () => {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  // dead letter: everything rejected ends up here
  await ch.assertExchange('orders.dlx', 'fanout', { durable: true });
  await ch.assertQueue('orders.dead', { durable: true });
  await ch.bindQueue('orders.dead', 'orders.dlx', '');

  await ch.assertExchange('orders', 'topic', { durable: true });
  await ch.assertQueue(queue, { durable: true,
    arguments: { 'x-dead-letter-exchange': 'orders.dlx' } });
  await ch.bindQueue(queue, 'orders', pattern);

  ch.prefetch(1);                                        // one unacked at a time
  console.log(`[${queue}] listening on ${pattern}`);

  ch.consume(queue, async (msg) => {
    const data = JSON.parse(msg.content.toString());
    console.log(`[${queue}] got`, data.key, 'redelivered:', msg.fields.redelivered);
    try {
      await new Promise(r => setTimeout(r, 3000));         // "work"
      if (data.key.includes('fail')) throw new Error('boom');
      ch.ack(msg);
      console.log(`[${queue}] done`);
    } catch (e) {
      ch.nack(msg, false, false);                        // no requeue → DLX
      console.log(`[${queue}] → dead letter`);
    }
  }, { noAck: false });
})();
    lock.js — distributed lock on Redis
    const Redis = require('ioredis');
const { randomUUID } = require('crypto');
const redis = new Redis();

const RELEASE = `if redis.call('get', KEYS[1]) == ARGV[1]
  then return redis.call('del', KEYS[1]) else return 0 end`;

async function acquire(key, ttlMs) {
  const token = randomUUID();
  const ok = await redis.set(key, token, 'PX', ttlMs, 'NX');
  return ok === 'OK' ? token : null;
}
const release = (key, token) => redis.eval(RELEASE, 1, key, token);

(async () => {
  const token = await acquire('lock:report', 10000);
  if (!token) { console.log('busy, skipping'); return redis.quit(); }
  console.log('lock is mine, working for 5 s…');
  await new Promise(r => setTimeout(r, 5000));
  console.log('released:', await release('lock:report', token));
  redis.quit();
})();

    Exercises

    Exercise 6 walkthrough: idempotent consumer

    The case we're catching: the worker finished the work and then died before the ack. RabbitMQ delivers the message again, and the work runs twice: a second email, a second charge. So every message has a messageId, and the worker remembers which ids it already handled. producer.js already accepts an id as the second argument, so node producer.js order.created.eu 42 run twice simulates a duplicate.

    Step 1 · in worker.js, a Set above ch.consume and two changes inside
    const processed = new Set();

ch.consume(queue, async (msg) => {
  const id = msg.properties.messageId;

  // 1. Duplicate: do nothing, but still ack,
  //    otherwise the message stays unacked
  if (processed.has(id)) {
    console.log(`[${queue}] duplicate ${id}, skipping`);
    ch.ack(msg);
    return;
  }

  const data = JSON.parse(msg.content.toString());
  try {
    await new Promise(r => setTimeout(r, 3000));
    if (data.key.includes('fail')) throw new Error('boom');

    // 2. Remember AFTER the work succeeds and BEFORE the ack
    processed.add(id);
    ch.ack(msg);
  } catch (e) {
    ch.nack(msg, false, false);
  }
}, { noAck: false });

    Order matters. If you add the id before the work and the work fails, the retry gets wrongly skipped as a duplicate.

    Step 2 · check it. Run one worker and send id 42 twice: the second one prints "duplicate". Now break it. Start a second worker on the same queue and send id 43 twice: round-robin sends each copy to a different process with its own Set, and both process it. Or restart the worker and send 42 again: the Set is empty after a restart. The worst part is that a restart after a crash is exactly the case we're defending against.

    Step 3 · production version: a table with a unique constraint
    CREATE TABLE processed_messages (
  message_id   text PRIMARY KEY,
  processed_at timestamptz NOT NULL DEFAULT now()
);

// worker.js (npm i pg)
ch.consume(queue, async (msg) => {
  const id = msg.properties.messageId;
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const r = await client.query(
      'INSERT INTO processed_messages (message_id) VALUES ($1) ON CONFLICT DO NOTHING', [id]);
    if (r.rowCount === 0) {                 // id already there: duplicate
      await client.query('ROLLBACK');
      ch.ack(msg);
      return;
    }
    // business write in the SAME transaction
    await client.query("UPDATE orders SET status = 'paid' WHERE id = $1", [orderId]);
    await client.query('COMMIT');
    ch.ack(msg);
  } catch (e) {
    await client.query('ROLLBACK');
    ch.nack(msg, false, false);
  } finally {
    client.release();
  }
});

    Why this holds up in every crash scenario:

    • Crash before COMMIT. Both the marker and the business write roll back. The message comes again and is processed normally.
    • Crash after COMMIT but before ack. The message comes again, the INSERT hits the conflict, rowCount = 0, and it's skipped with an ack.
    • Two workers get the same id at once. The second INSERT waits for the first to commit, then gets the conflict and skips.
    • Restarts and multiple instances. The table is shared and survives restarts.

    It's the same principle as in Module 1: INSERT … ON CONFLICT DO NOTHING is an atomic "check and write" in one statement. No lock needed.

    LimitsThe transaction only protects what lives in the same database. If processing means sending an email or calling a payment API, you can't put that call inside the transaction. Either pass your own idempotency key to the provider (most payment and many email services support it) so they drop the duplicate, or accept a rare double email where that's harmless. Clean old rows out of processed_messages periodically (say, older than 7–30 days): duplicates arrive within minutes or hours, not months.

    Cheat sheet and quiz

    When the system has…Reach for
    A slow operation inside a request (email, PDF, video processing)Queue + workers, respond 202, report status via polling or webhook
    One event, many reactionsFanout or topic exchange, one queue per service
    Traffic spikesQueue as a buffer, autoscale workers on queue length
    Write to the DB and notify othersOutbox pattern
    Duplicate messagesIdempotent consumer, dedupe by messageId
    A message that keeps failingRetry with backoff (TTL queue or delayed exchange) → DLQ + alert
    Ordered events per userConsistent hash exchange / partitions by userId, one consumer per partition
    "Only one instance does X"Redis lock with TTL and token; for critical data, a fencing token or an etcd lease
    Two purchases of the last itemAtomic conditional UPDATE or optimistic locking, no distributed lock
